## 2. G4-j — pg_cron execution: PARTIAL, with a real defect

### 2.1 What was proven

All 5 jobs are registered and `active = true`, with the URLs the route gate expects:

| jobid | jobname | schedule | runs ever | last run |
|---|---|---|---:|---|
| 9 | `cadence-reminder-dispatch` | `*/5 * * * *` | **897** | 2026-10-10 20:55 UTC |
| 10 | `cadence-reschedule-sweep` | `0 * * * *` | **74** | 2026-10-10 20:00 UTC |
| 11 | `cadence-memory-extraction` | `0 2 * * *` | 3 | 2026-10-10 02:00 UTC |
| 12 | `cadence-recurrence-materialize` | `0 1 * * *` | 3 | 2026-10-10 01:00 UTC |
| 13 | `cadence-goals-close-month` | `5 0 1 * *` | **0** | **never** |

Zero non-`succeeded` statuses across all 977 runs.

`net._http_response` holds **78 responses, 0 non-200**, with real bodies:

```json
{"runId":668,"checked":0,"sent":0,"failed":0,"skipped":0,"note":null}
```

### 2.2 Why that second query matters

`cron.job_run_details.return_message` reads `"1 row"`. That is **pg_net's queue
result**, not an HTTP status. A job that enqueues a request to a URL returning 404
would still report `succeeded` with `"1 row"`. `net._http_response` is the only
table holding the actual status code, so it is the only real proof.

This matters because `verify:cron-routes` (gate 9) proves the cron SQL and the
router agree on a *path*. It cannot prove the host is reachable or the secret
matches. The runbook said as much; this is the measurement that closes it.

### 2.3 DEFECT: `cadence-goals-close-month` has never fired and would 401

`runs_ever = 0`. Root cause is the secret plumbing, **not** the schedule.

Jobs A–D build their command like this (`lib/db/setup_supabase_cron.sql:158-170`):

```sql
SELECT cron.schedule('cadence-reminder-dispatch', '*/5 * * * *',
  format($job$SELECT net.http_post(url := %L || '/internal/dispatch',
    headers := jsonb_build_object('x-dispatch-secret', %L), body := '{}'::jsonb);$job$,
    current_setting('app.cadence.api_url'),
    current_setting('app.cadence.dispatch_secret'))   -- <-- interpolated NOW
);
```

`format()` **interpolates the value at schedule time** and stores the literal in
`cron.job.command`. That is why jobs A–D work and return 200 forever.

Job E in the live database is different — it reads the secret **at run time**:

```sql
headers := jsonb_build_object('Content-Type', 'application/json',
  'x-dispatch-secret', (SELECT current_setting('app.cadence.dispatch_secret', true)))
```

A plain `SET` is **session-local** (`setup_supabase_cron.sql:34-35` says so). The
cron worker's session has no such GUC, so `current_setting(..., true)` returns NULL,
the header carries no usable secret, and the request 401s on every tick.

Confirmed on the live project: `app.cadence.dispatch_secret IS NULL`, and
`app.cadence.api_url IS NULL`.

**Severity:** high, and silent. The job is registered, active, and green in
`SELECT * FROM cron.job`. Its first scheduled tick is **2026-11-01 00:05 UTC**, so
this would have surfaced as "monthly goals silently never closed" weeks from now.

### 2.4 Related: DISPATCH_SECRET is stored in plaintext

Because of the `format()` interpolation, jobs A–D embed the **live secret** in
`cron.job.command`. Anyone with `SELECT` on that table can read it, and it cannot be
rotated without unscheduling and recreating all four jobs. The file header
(`setup_supabase_cron.sql:20-22`) already identifies this as unacceptable — the
interpolation reintroduces it one step later.

`vault` schema and `create_secret`/`get_secret` are **available** on this project.
Storing the secret there and reading it at runtime fixes 2.3 and 2.4 together.

### 2.5 Owner remediation

Not applied: the database role in this session is `supabase_read_only_user`.

1. Store the secret: `SELECT vault.create_secret('cadence-dispatch-secret', '<value>');`
2. Re-register all five jobs reading
   `current_setting('vault.cadence-dispatch-secret', true)` at run time, or
   `(SELECT decrypted_secret FROM vault.decrypted_secrets WHERE name='cadence-dispatch-secret')`.
3. Re-run the `secret_handling` query in §2.6 — every row must read `secure:`.
