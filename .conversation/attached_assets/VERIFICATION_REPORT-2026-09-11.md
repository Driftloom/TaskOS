## 1. Summary

Closer to **"mostly real, narrow slice, with stale status docs"** than to "scaffolding pretending to be done." The three `PROGRESS.md` "Complete" modules (app shell + Clerk auth, task CRUD, Today/Inbox) are backed by real Drizzle/Express/Clerk code and a real React UI — no mocks, no `console.log`-wired buttons, no "Coming soon" counted as done, no hardcoded secrets. But the spec in doc 1 §8 defines 16 tables and the repo has 2 (`tasks`, `focus_sessions`); reminders, auto-reschedule, agent/memory, recurrence, Telegram, settings/export are genuinely absent (confirmed by code search, route mounts, and the OpenAPI spec — absence is verified, not assumed). Two statuses are stale in the *underclaiming* direction: Calendar Day/Week/Month UI and a persisted Focus timer already exist in code while `PROGRESS.md` still says "Planned." The biggest risks before new feature work are data-integrity hardening (a `demo-user` column default, missing FK, text-only status/priority with no DB constraint, `CORS origin:true`, no RLS — isolation is app-layer `where user_id = ?` only), plus the still-open doc-4 timezone-travel gap (no stored IANA timezone, no working/quiet hours anywhere). Typecheck could not be re-run on this Windows checkout (root `preinstall` requires `sh`), so the "full typecheck" part of the Complete claim is marked Unverifiable here, not confirmed.

## 3. The five doc-4 risks — addressed directly

1. **IANA timezone field + travel scenario (doc-4 §5b) — NOT addressed (checked hardest).** There is no `users` table at all, hence no `timezone` / `working_hours` / `quiet_hours` columns anywhere in code (grep: zero hits outside docs). What exists is request-scoped only: `?timezone` query param (max 64 chars) + `dayBounds(date, timezone)` computing local-midnight→UTC via `Intl.DateTimeFormat` with fallback to `"UTC"` on invalid input (`api-server/src/lib/date.ts:55-86`); client sends the browser zone (`App.tsx:115,333-336,616`). That handles "show me today in my current browser zone" but does NOT store a home zone, does NOT store working/quiet hours, and does NOT evaluate recurring wall-clock rules in a stored IANA zone. The doc-4 travel failure therefore still holds verbatim: home quiet hours cannot be distinguished from event-zone hours because neither is stored. No prior "timezone-safe fix" was found to debunk or confirm — `git log` (3 commits) shows no such message and `AUDIT.md` 2026-09-09 explicitly lists "timezone-aware scheduling" as still-separate work — but the gap itself is confirmed open. Required before reschedule/reminders: add `users.timezone` (IANA) + `working_hours`/`quiet_hours` evaluated in that zone, plus a change-timezone-mid-trip test (the existing DST-only test idea in doc-2 §5 does not cover it).
2. **Heartbeat / dead-man's-switch + kill switch (doc-4 §2) — NOT addressed.** There are no cron jobs to watch (no scheduler of any kind in the repo), no heartbeat table/check, no `cron.job_run_details` monitoring, no "pause all automation" flag. Saying plainly as instructed: absent. Since automation itself is absent, nothing is silently failing *today* — but the doc-4 requirement must be built *with* the first scheduled job, not after it. First dispatcher/sweep PR must include: run-log table, missed-check-in alert path, and a manual global automation kill switch.
3. **Parallel-run / rollout plan (doc-4 §3) — NOT addressed.** No coexistence criteria, no paper-fallback rule, no cutover trigger in code or docs beyond doc-2 §18's "run it for real for two weeks" (post-launch, no safety-net definition). Current narrow slice is safe to run alongside paper, but that is practice, not a plan. Before daily reliance: write the rule (e.g., paper + Cadence until N consecutive weeks of matching captures/reminders, with explicit fallback trigger).
4. **Paper-backlog import, photo → draft tasks (doc-4 §4) — NOT addressed.** No capture path of any kind for existing paper notes: no photo upload, no OCR/vision step, no draft-review queue. Quick-add is typed text only. Saying plainly: absent, and day-one fragmentation (paper archive vs empty app) is still the default outcome.
5. **Cost/spend tracking on LLM usage (doc-4 §5a) — NOT addressed (latent).** No agent exists so there is no spend *today*, but there is also no ceiling, no alert, no usage table, and doc-1 §12's open budget question is still open. Add the spend log + monthly alert as part of the agent PR, not later.
