# AUDIT — 2026-10-10 — Sign-up page (`/sign-up`)

**Scope:** `/sign-up` (Clerk `<SignUp>` + `clerkAppearance`) at `artifacts/cadence/src/App.tsx:106-144`, `App.tsx:202-214`.
**Mode:** Read-only. No source files were modified. `AUDIT.md` and `PROGRESS.md` untouched, per the append-only rule.
**Target measured:** `https://cadence-task-os.vercel.app/sign-up` (the build in the user's screenshot), at 1920×1080, 1280×900 and 390×844.

**Method.** Source reading is not sufficient here: the failure mode is a runtime cascade outcome, invisible in source. Evidence was gathered by driving headless Chrome over CDP against the deployed build and reading `getComputedStyle` — real values, not intent. Where a probe could not see something, that is recorded as untested rather than asserted.

---

## Implementation Integrity Verdict

**Pass, with a caveat.** The page is genuinely Cadence, not a Clerk default: it carries the app logo, the app's focus ring (`rgb(255,159,10)`, 2px, 2px offset) on every one of 8 tab stops, `bg-card`, `auth-card-w`, and the token-derived muted input fill. Nothing here is generic.

The caveat: **roughly a third of `clerkAppearance` is inert.** The author wrote `bg-accent` on the primary CTA, `text-foreground` on the Google button's label, and `border-border-control` on the inputs. All three classes are present in the DOM and all three are absent from the rendering. They are not dead classes — they emit CSS, and the repo's `verify-no-dead-classes` gate would pass them. They lose the cascade to Clerk's runtime constructable stylesheets (identifiable by the `🔒️` marker in the class list), which are injected after the app bundle and win same-specificity ties on the properties Clerk sets. This is a distinct failure class from the one the gate was built for, and it is currently unguarded.

## Executive Summary

The sign-up page is **functioning and correctly structured**, but it is visually broken in ways that source review cannot detect. Six control classes are written and none of them are reaching the screen.

- **7 defects**: 4 × P1, 5 × P2, 1 × P3.
- The **primary call to action has no background at all** — `Continue` renders as bold white text on a card with no button affordance.
- The **Google sign-in label renders at 1.22:1 contrast** — effectively invisible. This is the defect in the screenshot, and it is a confirmed real bug, not a Clerk loading state.
- **No control has a visible border.** `border-border-control` sets a border *color*; Tailwind preflight sets border *width* to `0`. The two halves never meet, so inputs and buttons render borderless.
- The page is **blue-accented while the app's accent identity is orange** — the CTA and link use `--accent`, but the focus rings use `--primary`.

## Detailed Findings

### [P1] Primary CTA renders with no background — no button affordance
- **Location:** `App.tsx:137` — `formButtonPrimary: 'bg-accent ${txtFg} font-bold hover:brightness-110 shadow-md'`
- **Category:** Theming / Implementation Integrity
- **Measured:** `backgroundColor: rgba(0, 0, 0, 0)`. The class `bg-accent` is present on the element; it produces nothing.
- **Impact:** "Continue" is the single most important element on the page. It reads as a line of text, not a button. The single strongest signal that a form can be submitted has been removed. This is the highest-impact defect on the page.
- **Root cause:** Clerk's base `.cl-formButtonPrimary` sets `background-color`; the app's `.bg-accent` has equal specificity and loses on source order. Compounding it, `App.tsx:114` sets `colorPrimary: 'hsl(var(--accent))'` — which is *also* not reaching the button, so there is no fallback path.
- **Recommendation:** Style the element through Clerk's own token (`colorPrimary`) rather than fighting its base rule with a utility class, and verify the computed background is non-transparent afterwards.
- **Suggested command:** `$impeccable colorize`

### [P1] "Continue with Google" label at 1.22:1 — effectively invisible
- **Location:** `App.tsx:132` — `socialButtonsBlockButtonText: txtFg`
- **Category:** Accessibility
- **Measured:** `color: color(srgb 0.1344 0.1344 0.1456 / 0.62)` on card `rgb(27,27,29)` → **contrast 1.22:1**
- **Standard:** WCAG 2.1 **1.4.3** (Contrast Minimum) requires **4.5:1** for 13px text. Fails by a factor of ~3.7.
- **Impact:** The Google label is `rgb(34,34,37)` at 62% opacity over a `rgb(27,27,29)` card — it is nearly the same colour as its own background. This is the dimmed text visible in the screenshot. Users relying on colour or low vision cannot identify the alternate sign-in path at all. The Google logo beside it renders in full colour, which makes the row look intentional rather than broken.
- **Root cause:** Same cascade loss. `text-foreground` is on the element and is not winning; Clerk's muted colour at 62% alpha wins.
- **Note:** This is the item the user flagged. Confirmed real — not a loading or hydration state.
- **Recommendation:** Drive the label colour through Clerk's `elements`/variables surface with verified output rather than a Tailwind utility.
- **Suggested command:** `$impeccable colorize`

### [P1] No visible border on any form control — `border-border-control` is half a class
- **Location:** `App.tsx:138` (`formFieldInput`), `App.tsx:139` (`socialButtonsBlockButton`), and every other `border-*` in the block
- **Category:** Accessibility / Theming
- **Measured:** `borderWidth: "0px"` on **all 7 controls**, while `borderColor` resolves correctly to a token value (`color(srgb 0.1344 0.1344 0.1456 / 0.11)`)
- **Standard:** WCAG **1.4.11** (Non-text Contrast) — control boundaries need 3:1.
- **Impact:** A border colour resolving to a token while the width is `0` is the most confusing possible failure: it looks configured and is invisible. Inputs read as a floating grey fill with no defined edge, which measurably weakens form affordance and makes the fields harder to parse visually.
- **Root cause:** Tailwind's `border-<color>` utilities emit **only** `border-color`. Preflight sets `border-width: 0` on `*`. The width must be set separately.
- **Why the existing gate misses it:** `verify-no-dead-classes` checks whether a class emits CSS. This class *does* emit CSS — it emits the wrong half. The gate correctly passes it and the defect ships anyway.
- **Recommendation:** Pair the colour utility with an explicit width, or move the boundary to a `box-shadow`/`ring` that carries both.
- **Suggested command:** `$impeccable harden`

### [P1] Show-password toggle: invisible and below the project's touch-target floor
- **Location:** rendered by Clerk's password field; not addressable from `clerkAppearance.elements` as written
- **Category:** Accessibility / Responsive
- **Measured:** `color: color(srgb 0.1344 0.1344 0.1456 / 0.41)` → **1.22:1**; size **32×26 px**
- **Standard:** WCAG **1.4.3** (fails, 4.5:1 required). WCAG **2.5.8** AA minimum 24×24 → **passes** at 32×26. WCAG **2.5.5** AAA and the project's own 44×44 rule (`DESIGN.md` §5, `AGENTS.md` §5) → **fails**.
- **Impact:** The control is present and correctly labelled (`aria-label="Show password"`), so it is operable by screen reader and by anyone who can find it — but at 1.22:1 the icon is effectively invisible to sighted users, and password masking is commonly the single biggest accessibility complaint in auth flows. Being able to reveal a password is the mitigation for exactly that problem.
- **Honest sizing:** this passes AA. It is reported because the repo set itself a stricter 44px bar, not because WCAG AA is breached.
- **Recommended command:** `$impeccable harden`

### [P2] CTA and link wired to `--accent` (blue), not `--primary` (orange)
- **Location:** `App.tsx:114` `colorPrimary: 'hsl(var(--accent))'`; `App.tsx:134` `footerActionLink: 'text-accent'`; `App.tsx:137` `bg-accent`

Per the design system, primary CTAs are Energy orange; `--accent` here is shadcn's subtle-surface slot, not the brand accent. The page does not read as Cadence even though it is branded — the logo is orange, the links are blue.
- **Recommendation:** Route CTA and link colour through `--primary`/`--primary-foreground`.
- **Suggested command:** `$impeccable colorize`

## Patterns & Systemic Issues

**1. The `clerkAppearance` block is unverifiable by construction.** It is a plain object of class strings. Nothing asserts that a class reached the screen, and the repo's existing guard cannot help — `verify-no-dead-classes` reads the built CSS and asks "does this class emit?", which is the wrong question for this surface. Here `bg-accent`, `text-foreground` and `border-border-control` all emit and all fail. **A gate that checks emission will never catch a cascade loss.** This is the same lesson as the deleted `no-raw-tailwind-spacing` rule, inverted: that gate failed correct code; this gap admits incorrect code silently.

**2. Half-class utilities are invisible to review.** `border-border-control` reads as complete and configured — the colour resolves. Only the computed `borderWidth: 0px` reveals it is inert. Any `border-<color>` without a companion width has the same defect, anywhere in the app, and the token lint will not flag it.

**3. Third-party component styling is being done through the wrong layer.** Tailwind utilities are being aimed at Clerk's internal elements, which is why they lose. The reliable surface is Clerk's `variables` and `elements` contract. The block currently mixes the two: `colorPrimary` (Clerk layer, partially working) and `bg-accent` (Tailwind layer, not working), with no consistent rule about which to use.

## Remediation Log — 2026-10-10 (appended after the audit above)

All changes are in **`artifacts/cadence/src/App.tsx` only**. `pnpm run verify` re-run after the change: **11/11 gates green in 46.1s**, 816 tests passing.

### Root cause, established by measurement

Clerk injects its component stylesheet at **runtime, after the app bundle**, and its base theme addresses controls through `[data-variant="…"]` attribute selectors. Three distinct override mechanisms were tried and only the third held:

| Attempt | Result |
|---|---|
| Tailwind utility on the element (`bg-accent`) | Lost — emitted CSS, never applied |
| Clerk style object, top level | Won for `background-color`, `color`, `min-height`, `font-size`, `border-radius`; **lost** to `[data-variant]` for `border-width` and `box-shadow` |
| Clerk style object under `'&[data-variant]'` | **Won** — same specificity as Clerk's base, emitted after it |

That third form is now the rule for boundaries, and it is why the border took three build cycles to land.

**The light-theme link was the one real trap, and it was caught by measuring rather than by the build.** `footerActionLink` declared `--primary`, which is `36 100% 50%` = `rgb(255,153,0)` — about **2.1:1 on the white card**, a clear 1.4.3 failure. ### [P2] NEW — controls lose their boundary entirely in forced-colors

Measured under `forced-colors: active`: the email input reports `border-top-width: 0px` **and** `box-shadow: none`.

This is a two-sided failure and neither side alone would be visible. Clerk's base theme zeroes `border-width` (that is the whole reason the boundary is expressed as a `box-shadow` ring — see the root-cause note above), and Windows High Contrast Mode then strips `box-shadow` as a decorative effect. The result is a form field with **no edge of any kind**, for exactly the users who need the edge most.

Text contrast in this mode is excellent (21:1 — HCM substitutes its own palette), and the focus ring is intact and uses the system focus colour (`rgb(26,235,235)`). So this is a boundary-only defect, not a general forced-colors failure.

- **Impact:** low frequency, high severity for those affected. Users relying on Windows High Contrast cannot see where the input fields begin and end.
- **Not fixed.** The honest fix is a real `border` with an explicit width that survives HCM, which means winning Clerk's `[data-variant] { border-width: 0 }` — the same fight already documented above, and one where `!important` is the only lever confirmed to work (validated against the live page during this audit). That is a deliberate, separate decision, not something to slip into a contrast pass.
- **Suggested command:** `$impeccable harden`

## Pass 3 — layout, light-theme CTA fill, and the missing theme toggle

Four further defects, all measured before and after. Files touched: `artifacts/cadence/src/App.tsx`, `tokens/tokens.json` (+ regenerated `tokens.css`/`tokens.generated.ts`), `scripts/verify-auth-surface.cjs`.

### [P1] The card had no fluid width at all — 347px at every viewport

`--component-dimension-auth-card-w` is `440px`, and `cardBox` declared `max-width` against it. **The declaration was dead.** Clerk's own `.cl-rootBox` caps itself near 380px and pads it, so the root box measured **347px identically at 390px, 768px, 1280px and 1920px** — a child cannot be wider than its container. The token was being read in the wrong place.

Fix: the outermost element now owns the constraint.

| | before | after |
|---|---|---|
| desktop / laptop / tablet | 347px | **440px** |
| phone (390px) | 347px | **358px** (fills the viewport minus the `<main>` gutter) |

### [P1] Vertical rhythm was one value repeated

Clerk shipped four unrelated gaps — 32 (card, form), 24 (main, field rows), 8 (label→input). Measured on `/sign-up`: **4 / 8 / 24 / 24 / 24 / 32 / 32**. Nothing was tighter *because* it was grouped, so proximity carried no meaning.

Replaced with a two-beat scale plus one accent:

| interval | value | meaning |
|---|---|---|
| title → subtitle | **8px** | heading and its own supporting line |
| label → input | **10px** | within a field group — tightest on the page |
| field → field, social → divider → form | **20px** | between peers |
| fields → primary CTA, and the three major regions | **24px** | before the action |

Measured after: **8 / 10 / 20 / 21 / 24**. Card height 683 → **667px** (`/sign-up`), 587 → **569px** (`/sign-in`).

Two of these needed margins rather than `gap`: the title/subtitle pair and the label/input pair both live inside an **unclassed** wrapper with no Clerk element key, so the extra pixels are bought with `marginBottom` and the effective gap is gap + margin. That is noted in the code at each site.

### [P1] Light-theme CTA fill — the 2.14:1 WARN, resolved

The 8-occurrence WARN was real. Computed, not eyeballed:

```
hsl(36 100% 50%)  rgb(255,153,0)  fill-vs-white 2.14:1  FAIL
```

**Darkening the fill alone cannot fix it.** Every orange dark enough to clear 3:1 against white drops the near-black `--primary-foreground` label below 4.5:1 — the two requirements point in opposite directions, which is exactly why this was deferred as a design decision:

```
hsl(32 95% 37%)  rgb(187,101,2)  fill 4.11 PASS   label 4.31 FAIL
hsl(30 95% 33%)  rgb(174,89,4)   fill 5.52 PASS   label 3.21 FAIL
```

The fix is to make the label **white**, which collapses both requirements into one number — with white on both sides, fill-vs-card and label-on-fill are the same ratio `1.05/(L+0.05)`. Chosen: `--primary: 30 95% 35%`, `--primary-foreground: 0 0% 100%`.

| | before | after |
|---|---|---|
| light CTA fill vs card (1.4.11, ≥3:1) | **2.14:1 FAIL** | **4.96:1 PASS** |
